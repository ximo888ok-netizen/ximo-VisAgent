# 诊断：为什么这个 Agent "不够聪明"（2026-09-16）

> 数据来源：`%APPDATA%\ximo-VisAgent\audit.db` 真实任务流水（62 个任务，已独立复核）+ 四路代码审计（观察通道 / 动作空间 / 记忆与推理预算 / 失败现场挖掘）。所有结论带 文件:行号 或数据库计数。

## 一、真实表现

| 状态 | 数量 | 占比 | 平均步数 | 平均 token |
|---|---|---|---|---|
| COMPLETED | 16 | 25.8% | 12.3 | 88k |
| **EMERGENCY_STOPPED** | **33** | **53.2%** | 26.4 | 178k |
| FAILED | 10 | 16.1% | 37.1 | 209k |
| CANCELLED / RUNNING | 3 | — | — | — |

失败原因：EMERGENCY_STOP 33、MAX_STEPS 9、LLM_ERROR 1。

**两个关键读数**：
1. 成功任务平均只用 12.3 步，一旦任务变长（>25 步）基本就以超步数或被人工中止收场——**它不是"一直笨"，是"撑不住长任务"**。
2. `EMERGENCY_STOPPED` 经代码核实是**用户手动急停**（`island.handlers.ts:59` reason 默认 `"user-request"`；`hotkeys.ts:16-19` 全局 Ctrl+Alt+Q → `emergencyStopAll()`；内部守卫产生的状态是 `FAILED`/`MAX_STEPS`，见 `loop.ts:157-182`）。所以 33 次的含义是：**超过一半的任务，是人看着它跑偏之后自己按下的停止键**，平均忍到 26.4 步。这是比"自动失败"更强的负面信号。内部守卫误判（R3）仍然存在，但它是"让人更想按停止"的帮凶，不是这 33 次的直接原因。

## 二、根因（按对"聪明程度"的影响排序）

### R1 默认配置下它根本不思考 —— 一行代码
`config-store.ts:74` 默认 `thinkingMode:'daily'`，注释自陈"恒关，最快"；映射见 `openai-compat.ts:126`。即默认档位下 **30/30 步全部不思考**，`thinkingEffort:'high'` 只对 DeepSeek 生效（`:42-49`）。用户"没人类一半灵活"的直觉在配置层面就是事实。

### R2 看得见图，但说不准位置、看不到结构（最大结构性差距）
先纠正一个容易误读的说法：**它没被蒙眼**——每步都拿到全屏物理像素 JPEG（质量 95、无降采样，`host-capabilities.ts:19-28`、`vision.ts:17-20`）。真正的短板是"手眼协调"：
- **从图上读坐标是它最弱的一环**：靠 100px 网格目测，代码注释自认 flash 级模型目测"±20-50px 必点飞"（`schema.ts:95`），而 UIA 给的是精确 rect。
- **结构清单不主动给**：每步观察文本只有步号/目标/前台标题/分辨率/≤6 个窗口标题（`loop-helpers.ts:42-102`）。要知道"这窗口上有什么能点"，得它自己一个词一个词去问。
- **问了也只给名字不给坐标**：`ui_locate` 返回 ≤8 个候选的 `#id "name"(type)`，**rect 只进 data、模型看不到**（`executor.ts:261,268-270`）——数据在手边却被扔掉了。
- **强观察工具是按需加载的**：`look_close / screen_ocr / wait_for` 都要先花一轮 `request_tools`（`schema.ts:170-227`），弱模型经常不知道要加载。
- **SoM 候选会被上一任务残留污染**：日志实证 `ui_locate{qry:"卸载"}` 返回"番茄意面""13.mp4"，模型照点。
- **动作后是固定毫秒等待**：点击 300ms、打字 150ms、开应用 400ms（`click-verify.ts:44`、`keyboard-verify.ts:72`、`executor.ts:23`），无条件等待默认生效 → 慢界面必然截到过渡帧。

### R3 守卫误杀：把正确行为判成死循环
- 整帧 8×8 pHash 阈值 **6/64 bit**（`loop-helpers.ts:19-28`）：改一个单元格、数字变了常常翻不动 6 bit → 报"画面没变" → 连续 3 步触发停滞并**硬拦截重复动作**（`loop-efficiency.ts:20,110-124`）→ 急停。
- 点击效果延迟 >300ms 被误报"可能未生效，换方案"（`click-verify.ts:40-44`），把模型从正确路径上推走。
- 连点熔断给出的建议是"坐标至少偏移 50px"（`click-guard.ts:16-71`）——目标若是 12×12 小图标，这个建议必然点飞。
- 净效果：日志里"连点同一坐标 8-10 次"与"3 次即熔断拦截"同时存在，说明**判据在两个方向上都不准**。

### R4 动作空间缺口 + 提示词自相矛盾
- `mouse_click` 只有 `x/y/button/times`，**没有修饰键**（`schema.ts:14-19`），而系统提示词第 72/75 行明确教它"点击起点→Shift+点击终点""Ctrl+点击多选"——**照做必错**（点了没修饰）。
- 完全没有：hover（tooltip/悬停菜单）、scroll-to-element、表单级批填（`safety.ts:46-49` 有 `submit_form` 策略但 schema 里无此工具 = 死条款）。
- 残缺：`parseCombo` 对符号一律抛"未知按键"（`win32-keyboard.ts:41-51`，Ctrl+/Ctrl+逗号等做不到）；剪贴板只支持文本（`executor.ts:228-236`）；拖拽只能坐标→坐标，拖文件到窗口基本不可用。
- 批执行由模型自觉划分、**批内零感知**（`loop.ts:315-415`、`system.ts:21`），前一步"成功但没生效"时后续盲动作照跑。

### R5 学习闭环是断的（写侧没接线）
`insertRecoveryRule` 只有 store 定义（`experience-store.ts:142`、`evolution-store.ts:147`），**全仓无任何生产调用方** → 恢复规则库永远为空 → 同一目标连败 5 次（"卸载小答AI客服"，30~101 步）每次走完全相同的路。它是"重复撞墙直到止损"，不是"吸取教训"。

### R6 长任务失忆
滑窗仅 5 步、每步结果截 60 字、≥40 步才压缩（`memory.ts:13-14,85`）。第 55 步看第 5 步只剩摘要 → 重做已完成的事、忘记为什么放弃过某条路。

### R7 无 replan、常识注入不及时
计划只是随每步注入的一行文本（`loop-helpers.ts:47-49`），无逐步核销、无 replan 动作，只有 1/3、2/3 两处里程碑一句话纠偏（`milestone.ts:16-19`）。`WINDOWS_KNOWLEDGE` 不随任务下发、困境才补发一次（`system.ts:39-82`、`loop.ts:261`）；能力卡仅 9 张种子。

### R8 度量赛道是假的（为什么我们没早发现）
`e2e/tasks.mjs` 四条基准（记事本中文/计算器/Excel 求和/IM 发送）**全部走 open_app + file_write 等工具直写，绕开真实 GUI 点击**，审批默认放行。所以 `TEST_REPORT.md` 198 例全绿的同时，真实任务成功率只有 26%。**绿灯测的是一条不存在的赛道。**

## 三、优化路线（按 ROI 分波）

### 第 0 波 · 先建真赛道基线（半天，其他所有改善的前提）
新增 5-8 条**真实 GUI 点击流** e2e（第三方软件主界面、卸载向导、浏览器搜索下载、多窗口搬运、Excel 透视、进度等待），以「完成率 / 急停率 / 每任务审批次数」为北极星指标，跑出改动前基线。没有它，后面每一波都是凭感觉。

### 第 1 波 · 止血（1 天，改动极小、收益立竿见影）
1. 默认思考档 `daily → long`（或直接 auto），一行；
2. 变化判定从"整帧 6bit"改成**优先看点击目标区域的局部 diff**（复用已落地的 `changed-region.ts`），整帧只作辅助；
3. 停滞/熔断的处置从"拦截+劝"改为**强制换策略**：先自动升级观察（zoom / ui_locate 带坐标 / OCR），而不是继续烧步数；
4. 熔断建议文案去掉"偏移 50px"，改为"改用 ui_locate 精确定位"；
5. 点击后改**条件等待**（等到画面稳定或元素出现，上限 N ms）。

### 第 2 波 · 撑开观察带宽（2-3 天，最大杠杆）
1. 每步主动附带**前台窗口可交互元素清单**（UIA 裁剪：可点击 + 有名 + 视口内，上限 ~40 条，带 rect 与状态），把"盲探"变"看着清单干活"；
2. `ui_locate` summary 带上坐标；
3. `look_close / screen_ocr / wait_for` 从按需加载改常驻（或至少把 `wait_for` 常驻）；
4. SoM 候选加 query↔name 一致性校验 + 任务间清空缓存。

### 第 3 波 · 补齐动作原语 + 提示词对齐（2 天）
1. `mouse_click` 加 `modifiers`（Ctrl/Shift/Alt）——先让提示词已经教的东西真能做；
2. `scroll_to`（滚到元素可见）、`wait_for` 扩展（等文件生成/下载完成/进度稳定）；
3. 表单批填动作（一次点+填多字段）；剪贴板支持文件/图片格式；
4. **提示词↔工具能力一致性审计**：做不到的建议一律删或实现。

### 第 4 波 · 让它会学习、不忘事（3-4 天）
1. 接通失败归因 → `insertRecoveryRule`（低危 hint 免人批），复活 recovery 规则库；
2. 加 `replan` 动作 + 里程碑 drift 时自动重跑计划；
3. 窗口 5→8 步、压缩改 token 驱动、失败原因保留原文；
4. 能力卡扩到 30+ 并随任务常驻注入 top-k。

## 四、必须坦白的能力天花板

人类灵活性的三个来源我们结构上就缺：**连续视觉流**（我们是每步一张静态图）、**动作并行与微操**（我们一步一次离散决策）、**海量世界先验**（我们 9 张能力卡 + 一段硬编码常识）。此外当前默认用 flash 级模型目测坐标，代码注释自认"±20-50px 必点飞"（`schema.ts:95`）——换更强的 grounding 模型能提升，但成本上升。

所以合理预期是：第 0-3 波做完，**长任务急停率从 53% 显著下降、真实任务完成率明显上升**；但"人类一半灵活"这个标准，靠这些改造能靠近、不能一步达到。
